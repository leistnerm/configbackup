# Git / GitHub snapshot storage

ConfigBackup can use Git as the history engine for selected tasks. Git is especially useful for text-oriented configuration, SQL schema, expanded SSIS package XML (`.dtsx`), PostgreSQL schema, system inventory, and other artifacts where line-level diffs are useful.

A task supports:

```yaml
storage: filesystem   # dated ConfigBackup history only
storage: git          # current snapshot in Git; Git provides history
storage: both         # both dated history and Git history
```

`execute` tasks prepare artifacts and do not archive them directly. Use a dependent `file`, `directory`, `glob`, or `command` task for storage.

## Recommended mode for an existing/shared repository

For an existing repository that people also use for other content, use **pull-request mode**:

```yaml
git:
  repository: 'S:\Repos\Infrastructure'
  mode: pull_request
  remote_name: origin
  base_branch: auto
  branch: 'configbackup/{hostname}'
  path_prefix: configbackup
  include_hostname: true
  push: true

  # Git-only exclusions. The files may still be retained by storage: both.
  ignore:
    - '**/*.ispac'

  author_name: ConfigBackup
  author_email: configbackup@example.invalid
  commit_message: 'ConfigBackup {hostname} {date} ({run_id})'

  pull_request:
    enabled: true
    provider: github
    # Usually leave this as auto; ConfigBackup derives OWNER/REPO from origin.
    repository: auto
    draft: false
    title: 'ConfigBackup: {hostname}'
    body: |
      Automated configuration snapshot for {hostname}.

      Generated by ConfigBackup {version}.
    reviewers: []
    labels: []
```

In this mode ConfigBackup does **not** switch branches or stage files in the repository's normal checkout. Instead it:

1. fetches `origin`;
2. detects the remote default branch when `base_branch: auto` is used (`main`, `master`, or another default);
3. creates/refreshes an automation branch such as `configbackup/SERVER01`;
4. creates an isolated linked Git worktree for that branch;
5. writes only the ConfigBackup snapshot into that worktree;
6. stages only the ConfigBackup-managed subtree;
7. commits changes only when the snapshot changed;
8. pushes the automation branch;
9. creates a GitHub pull request if one is not already open; or reuses the existing open PR on later runs;
10. removes the temporary linked worktree.

Git linked worktrees have their own working tree and index, so unrelated staged or unstaged work in the normal checkout is not touched.

### Stale ConfigBackup worktrees

If a process is interrupted while a linked worktree is being created or removed, Git can retain a registration that keeps the automation branch checked out. ConfigBackup automatically prunes missing worktrees and removes stale worktrees only when their paths are under a recognized ConfigBackup temporary worktree root. This includes both the current `${TEMP}/cbwt/<short-id>` layout and the older 1.4.0 `${TEMP}/configbackup/.../git-worktrees/...` layout.

ConfigBackup will **not** automatically remove a worktree at an unrelated path. If the configured automation branch is intentionally checked out elsewhere, switch/remove that worktree manually or choose a different `git.branch`.

Manual inspection/recovery commands remain available:

```bash
git -C /path/to/repository worktree list
git -C /path/to/repository worktree prune -v
```

### Worktree location and Windows long paths

By default ConfigBackup keeps the temporary linked worktree path intentionally short:

```text
<TEMP>/cbwt/<short-id>
```

On Windows this is typically similar to:

```text
%TEMP%\cbwt\a1b2c3d4e5f6
```

The short ID is stable for the repository + automation branch. This preserves path-length budget for repositories containing long SSIS/package/object names. ConfigBackup also invokes Git with `core.longpaths=true` on Windows for its own commands; it does not need to modify the user's global Git configuration.

Override the base directory when desired:

```yaml
git:
  worktree_root: 'C:\cbwt'
```

The actual worktree will be created beneath that root using the same short ID, for example `C:\cbwt\a1b2c3d4e5f6`. The directory is temporary and is removed/pruned after the run.

If a prior ConfigBackup PR was merged/closed, a subsequent run starts the automation branch again from the current remote base branch. If an open PR exists, later ConfigBackup commits are pushed to the same branch and therefore update that PR.

### Base branch selection

`base_branch: auto` asks the remote for its symbolic `HEAD`. This normally follows whatever the repository currently uses as its default branch.

You can pin it explicitly:

```yaml
git:
  base_branch: main
```

### PR automation is optional

If you want another scheduled process to create the PR, disable only the PR step:

```yaml
git:
  mode: pull_request
  push: true
  pull_request:
    enabled: false
```

ConfigBackup will still create/update/push the automation branch. A separate script can then use `gh pr create`, an API, Azure DevOps CLI, GitLab CLI, etc.

At present ConfigBackup's built-in PR provider is GitHub via the `gh` CLI. Git branch/worktree storage itself remains provider-neutral.

### GitHub repository selection

By default, `git.pull_request.repository: auto` derives the GitHub repository from `git.remote_name` (normally `origin`) and supplies it to `gh` explicitly through `GH_REPO`. This means PR creation does not depend on the directory from which ConfigBackup was launched and does not depend on `gh` inferring a repository from the temporary worktree.

For GitHub.com, an origin such as `https://github.com/ORG/REPO.git` or `git@github.com:ORG/REPO.git` resolves to `ORG/REPO`. GitHub Enterprise remotes resolve to `HOST/ORG/REPO`.

Override it when necessary:

```yaml
git:
  pull_request:
    enabled: true
    provider: github
    repository: ORG/REPO
```

or for GitHub Enterprise:

```yaml
repository: github.example.com/ORG/REPO
```

## Git-only ignores

Use `git.ignore` for files that should remain available to filesystem history but should not be committed to Git:

```yaml
git:
  ignore:
    - '**/*.ispac'
    - '**/*.bak'
```

Patterns are matched relative to ConfigBackup's Git snapshot root. ConfigBackup writes a managed block into a `.gitignore` inside that snapshot root and preserves any lines outside its managed block.

For example:

```yaml
tasks:
  - name: sql-server
    type: directory
    source: ${SQL_STAGING}
    destination: sql-server
    storage: both
```

with:

```yaml
git:
  ignore:
    - '**/*.ispac'
```

means:

- the dated filesystem archive **does retain** `.ispac` files;
- the Git snapshot **does not contain** `.ispac` files;
- expanded `.dtsx`, `.sql`, `.json`, `.csv`, and similar files can still be diffed normally;
- if an `.ispac` was previously tracked, ConfigBackup removes it from the current Git snapshot and commits that deletion. Its older Git history still exists.

Git's own `.gitignore` semantics do not untrack already tracked files, so ConfigBackup explicitly removes previously tracked matching snapshot files when a new ignore rule is introduced.

Negated patterns (`!pattern`) are intentionally not supported by ConfigBackup's `git.ignore` option; keep the rules simple and explicit.

## Snapshot path layout

The effective Git destination is:

```text
<git.repository>/<git.path_prefix>/<hostname if enabled>/<task destination>
```

Example:

```yaml
git:
  repository: 'S:\Repos\Infrastructure'
  path_prefix: configbackup
  include_hostname: true
```

and:

```yaml
- name: sql
  destination: sql-server
  storage: git
```

produces approximately:

```text
Infrastructure/
  configbackup/
    SERVER01/
      sql-server/
        ...
```

## Direct mode

`mode: direct` is retained for dedicated ConfigBackup repositories:

```yaml
git:
  repository: 'C:\ConfigBackupGit'
  mode: direct
  branch: main
  push: true
```

Direct mode operates in that working tree and therefore requires the entire working tree to be clean before ConfigBackup begins. For existing/shared repositories, prefer `mode: pull_request`.

## Git identity

ConfigBackup sets the commit identity inside its active Git working tree:

```yaml
git:
  author_name: ConfigBackup
  author_email: configbackup@example.invalid
```

You may also configure the OS account globally:

```bash
git config --global user.name "ConfigBackup"
git config --global user.email "configbackup@example.invalid"
```

Inspect effective configuration:

```bash
git config --list --show-origin
```

# Authentication and credential setup

Credentials are deliberately **not** stored in ConfigBackup YAML. Do not put a token/password/private key into `remote_url`.

The scheduled job must run as the same OS identity whose Git/SSH/GitHub CLI credentials were configured.

## Verify the repository and remote

From the account that will run ConfigBackup:

```bash
git -C /path/to/repository status
git -C /path/to/repository remote -v
git -C /path/to/repository ls-remote origin
```

For an existing repository, ConfigBackup uses its configured remote. You do not need to clone a second copy; PR mode creates a temporary linked worktree itself.

## Windows HTTPS: Git Credential Manager

Git for Windows commonly includes Git Credential Manager (GCM).

Verify:

```powershell
git --version
git credential-manager --version
```

Configure it if needed:

```powershell
git config --global credential.helper manager
```

Use a normal HTTPS remote, without credentials embedded in it:

```powershell
git remote -v
git ls-remote origin
```

Perform one authenticated Git operation interactively as the same Windows account that Task Scheduler will use. GCM then uses that account's credential store.

Test write access without changing the remote:

```powershell
git push --dry-run origin HEAD:refs/heads/configbackup-auth-test
```

A Task Scheduler job running under another user/service identity will not automatically see your interactive user's stored credentials.

## SSH authentication: Windows or Linux

Create a dedicated key under the account running ConfigBackup:

```bash
ssh-keygen -t ed25519 -C "configbackup@HOSTNAME" -f ~/.ssh/configbackup_ed25519
```

Protect it on Linux:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/configbackup_ed25519
chmod 644 ~/.ssh/configbackup_ed25519.pub
```

Add only the **public** key to the Git hosting provider. A repository-scoped deploy key with write permission is often a good fit for unattended configuration collection.

Example `~/.ssh/config`:

```text
Host github-configbackup
    HostName github.com
    User git
    IdentityFile ~/.ssh/configbackup_ed25519
    IdentitiesOnly yes
```

Then configure/use a remote such as:

```bash
git@github-configbackup:ORG/REPOSITORY.git
```

Test it:

```bash
ssh -T git@github-configbackup
git ls-remote origin
```

Do not disable SSH host-key checking. Verify the provider's published SSH host-key fingerprints before populating `known_hosts`.

### Passphrases and unattended execution

A passphrase-protected key is preferable when the scheduled job has reliable access to an `ssh-agent`:

```bash
ssh-add ~/.ssh/configbackup_ed25519
```

For a tightly restricted service account where an agent is impractical, a repository-scoped deploy key without a passphrase can be operationally simpler, but protect the private-key file carefully.

## Linux HTTPS: Git Credential Manager

GCM also runs on Linux, but Linux requires an explicit credential store. Depending on the host, options include a Secret Service/libsecret store, GPG-backed storage, or a transient cache.

Example:

```bash
git config --global credential.helper manager
git config --global credential.credentialStore gpg
```

For headless servers, SSH deploy keys generally have fewer dependencies.

Avoid Git's plaintext credential helper for production automation:

```bash
git config --global credential.helper store
```

It writes credentials to a plaintext file.

# GitHub CLI PR setup

Built-in PR creation requires the GitHub CLI (`gh`) on PATH.

Verify/install separately, then authenticate as the scheduled-task account:

```bash
gh --version
gh auth login
gh auth status
```

For HTTPS Git operations, GitHub CLI can also configure itself as Git's credential helper:

```bash
gh auth setup-git
```

For headless automation, GitHub CLI can also use its documented environment-token mechanisms; keep those secrets in the scheduler/service secret environment, **not** in ConfigBackup YAML.

Before enabling PR automation, verify noninteractive access:

```bash
gh auth status
gh repo view
git ls-remote origin
```

ConfigBackup creates PRs noninteractively with explicit base/head/title/body flags. An existing open PR for the configured automation branch is reused rather than duplicated.

# Commit and failure behavior

ConfigBackup creates one commit for a successful run only when Git-backed content actually changed. An unchanged snapshot creates no empty commit.

In PR/worktree mode, failure does not reset, stash, or clean the user's normal checkout. The isolated automation worktree is discarded instead.

Confirmed source deletions become normal Git deletions after ConfigBackup's missing-run and mass-deletion safety checks. Prior content remains in Git history.

Filesystem retention policies do not rewrite Git history. `storage: both` therefore combines ConfigBackup's retention engine with ordinary Git commit history.

# Binary artifacts

Git can store binary files, but large/changing binaries do not produce useful text diffs and can grow repositories quickly. For the SQL Server collector, the recommended configuration is:

```yaml
git:
  ignore:
    - '**/*.ispac'
```

and:

```yaml
storage: both
```

This keeps the deployable `.ispac` in the filesystem archive while Git tracks the expanded SSIS content.

If binary artifacts must be kept in Git, consider Git LFS according to your organization's repository policy.

# Security

The collected files can themselves contain operationally sensitive information even when authentication secrets are excluded. Examples include SQL Agent command lines, SSIS XML, service arguments, firewall/network configuration, users/groups, and application configuration. Use a private repository with appropriate access controls and inspect collector output before enabling automatic pushes/PRs.
